# Independent test plan

The independent tester works from a clean worktree and reports each case as Passed, Failed, Blocked, or Not Run with mutation ID, bill ID/number, event ID, timings, and database evidence.

## Characterization

Cover timed/unit-sale sessions; original/edited times; pause variants; direct/multi-hop carryover; session/tab items; cigarettes; variants; reusable inventory; game and consumables combos; cash/UPI/split/deferred/partial collection; settlement during checkout; discounts/LTP/rounding/zero guards; replacement quantity deltas; receipts; payments; stock; audits; and downstream reports.

## SQL transaction and security

Assert exact normalized rows and complete rollback on failure. Prove the `app_state` data hash and row metadata are unchanged. Reject anonymous, inactive, wrong-organization, actor-spoof, malformed, stale, already-closed/billed, insufficient-stock, invalid-replacement, invalid-discount, and over-settlement requests.

## Idempotency and concurrency

Use two independent connections for same-mutation replay, lost response, double click, same session/tab, shared hopped session, shared pending bill, limited stock, duplicate bill number, and checkout concurrent with settlement, admin inventory save, reject, hop, replacement, void/refund, and live item/combo writes. Require no duplicates, negative stock, over-settlement, deadlock, stale success, or global-row wait.

For checkout versus standalone settlement, first run the read-only `npm run test:db:staging:v2:checkout-settlement-race:preflight`, then run only `npm run test:e2e:staging:v2:checkout-settlement-race`. The serial staging-only case SHALL create a real deferred pending bill, start a second timed session for the same customer through the pending-bill warning, and prepare both the checkout's previous-dues collection and Bill Register's standalone full settlement through separate authenticated browser contexts. Capture each UI-generated RPC exactly once before either reaches the database, prove both commands target the same pending bill with its exact expected due, and submit both commands concurrently with zero retries. Either lock winner is valid: checkout victory SHALL make standalone settlement fail with `financial_adjustment_conflict`, while standalone-settlement victory SHALL make checkout fail with `settlement_conflict`. Exactly one mutation, one settlement payment, one `bill_settled` audit, and one mutation-scoped event SHALL persist; the pending bill SHALL become fully issued/paid and the losing mutation lookup SHALL return null. If standalone settlement wins, reconcile the financial outcome before cleanup, then reject the unbilled second session through a separately identified, identity-bound `npm run test:e2e:staging:v2:checkout-settlement-race:cleanup` execution without retrying checkout, and run the exact after-cleanup reconciler. Prove the `app_state` version and full data hash do not change across the two financial commands; a later operational rejection may advance compatibility only through its exact acknowledged cleanup event.

For checkout versus an admin inventory save, require the admin command to carry the stock value observed before the race. If checkout wins the normalized item lock, the admin request must roll back with `inventory_conflict`; if the admin save wins, checkout must apply its delta to the newly committed stock. In neither ordering may the admin snapshot restore stock consumed by the bill. Verify that the precondition field is absent from normalized `raw_data` and `app_state.data`.

For checkout versus a direct live session-item mutation, use one dedicated positive-price stock item and one active timed session in three separately identified zero-retry orderings: checkout-first, `add_session_item`-first, and simultaneous. Capture and submit each UI-generated command exactly once from independent authenticated contexts. Both contexts SHALL authenticate as distinct active authoritative admins. If the ignored base credential slots resolve to one actor, provision exactly one run-bound temporary staging admin through `npm run test:e2e:staging:v2:checkout-session-item-race:admin:create`; bind slot B to its checkpointed actor without printing the password, retain it through race reconciliation and any recovery cleanup, then deactivate it through the exact lifecycle command and immutable postflight evidence. A checkout winner SHALL commit one canonical bill and make the stale item command fail with the exact session-not-open conflict and zero item/reservation/audit/event effect. An item winner SHALL commit one exact session item, reservation, audit, and operational event; the stale checkout SHALL fail its server-authoritative source-item validation with a null financial mutation and no bill/payment/financial event. A simultaneous run may produce only one of those two canonical outcomes. Reconcile exact command cardinality, actor attribution, session status, item/reservation/stock arithmetic, bill/payment/mutation/event/audit rows, and `app_state`: the financial winner does not change compatibility, while only an acknowledged operational winner or identity-bound rejection cleanup may advance it. Every run SHALL end with an exact empty-floor postflight and SHALL not retry an ambiguous command. After checkout-first is already immutably reconciled, the separately reviewed `npm run test:e2e:staging:v2:checkout-session-item-race:remaining-two` mode MAY execute only item-first and simultaneous; its read-only list and preflight variants SHALL bind the same exact ordered selection through preflight, browser checkpoints, recovery, and final postflight. After reload, conflict recovery SHALL clear a rendered persisted conflict and accept Synced without clearing only after it remains stable long enough to exclude delayed hydration.

For checkout versus refund, first run the read-only `npm run test:db:staging:v2:checkout-refund-race:preflight`, then run only `npm run test:e2e:staging:v2:checkout-refund-race`. The serial staging-only case SHALL create one uniquely named stock item with opening stock 2 and two uniquely named customer tabs. It SHALL issue the first one-item bill, reserve one unit on the second tab, prepare the second checkout and a refund of the first bill in separate authenticated browser contexts, capture each UI-generated RPC exactly once, and submit both commands concurrently with zero retries. Both commands SHALL commit exactly once: two Rs 50 issued payments remain, the first bill becomes refunded with no fabricated payment, stock movements are exactly sale -1, sale -1, and reversal +1, final stock is 1, both tabs remain closed/billed, and all bill, payment, movement, audit, event, and lifecycle actors match the authenticated contexts. The financial race SHALL leave the `app_state` version and full data hash unchanged. Archive only the exact QA item afterward through one acknowledged admin command, prove that this alone advances compatibility once, and require an empty staging floor. Any incomplete or ambiguous attempt SHALL stop without retry and run `npm run test:db:staging:v2:checkout-refund-race:reconcile`. A separately identified cleanup may run only from the reconciler's exact recovery artifact through `npm run test:e2e:staging:v2:checkout-refund-race:cleanup`; it SHALL bind every authorized tab, item, bill, line, payment, movement, mutation, event, audit, actor, and compatibility hash before mutating, and `npm run test:db:staging:v2:checkout-refund-race:cleanup-postflight` SHALL prove the exact terminal state before another race run.

## UI/reload/realtime

Use two staging browsers. Verify confirmation-bound modal behavior, canonical receipt/PDF, compact realtime, hard refresh, Bill Register, pending receivables, dashboard, analytics, reports, customer history, inventory report, actor attribution, event-before-response ordering, and recovery after a missed realtime event.

Run repeatable UI cases through the staging-only Playwright harness instead of conversational browser automation. The runner SHALL accept only the exact ordinary staging hostname and staging Supabase project, require financial v2 to remain false for Release A, load credentials only from ignored environment state, use two independent browser contexts, set retries to zero, disable traces so password-fill values cannot be persisted, and retain screenshots/video only on failure. Every mutation case SHALL attach compact JSON RPC evidence and SHALL confirm cleanup. An ambiguous checkout or cleanup acknowledgement SHALL stop without an automatic retry and require database reconciliation.

For multi-hop checkout contention, the harness SHALL create a real three-session chain through two `hop_session` and two continuation `start_session` UI flows. Reconciliation scheduled for an already consumed hop SHALL be identity-bound and must not clear a newer hop's continuation modal. Both browser contexts SHALL independently prepare the final checkout, capture one v2 command each, submit each distinct mutation exactly once, and perform no winner replay. Exactly one command SHALL commit; the loser SHALL return `session_not_billable` with a null mutation-status lookup. All three sessions and exactly three linked session-charge lines SHALL point to the one winning bill, the losing bill/event/audits SHALL be absent, authenticated actor attribution SHALL match the winning JWT, and both the `app_state` version and data hash SHALL remain unchanged across the financial race.

Before sending a multi-hop checkout, compare every carried session's submitted start/end instants with the typed normalized database columns. A capture-only diagnostic SHALL abort and await interception completion without sending the checkout. Characterization SHALL prove typed start/end override stale compatibility JSON, typed null end suppresses a stale raw end, and the explicitly retained legacy null-start fallback. A disposable timing-edit then hop case SHALL prove `sessions.started_at`, `sessions.raw_data.startedAt`, and the compatibility session start remain identical before production promotion.

For checkout-versus-hop coverage, capture each UI command exactly once and execute checkout-first, hop-first, and simultaneous orderings. If the scenario edits a previously persisted hop end time and expects checkout to succeed, prove both captured JWTs have authoritative active organization-admin membership through `current_user_org_role` before either command is sent. Reconcile the session, bill, payment, mutation, events, audits, actors, and compatibility version. Prove a successful hop followed by checkout transitions the observer from `closed/hopped` to `closed/billed`, closes `Continue Customer` before refresh, and remains closed after refresh; prove a losing hop shows the exact conflict alert without retrying.

Run the ordinary-staff timing matrix only through `npm run test:e2e:staging:v2:roles` with two distinct staging-only accounts loaded from ignored `.env.e2e.roles.local`. A separately approved partial lifecycle MAY use `npm run test:e2e:staging:v2:roles:remaining`; that exact mode SHALL select only the role preflight plus hop-first and simultaneous cases. After the receptionist-checkout/manager-hop hop-first case is evidenced, `npm run test:e2e:staging:v2:roles:remaining-three` SHALL select only the role preflight, the opposite hop-first direction, and both simultaneous directions. Both list variants SHALL remain read-only. The dedicated runner SHALL reject arbitrary spec/path arguments, multiple modes, and unknown modes. The serial preflight and every mutation case SHALL prove slot A is an active authoritative `org-primary` receptionist, slot B is an active authoritative `org-primary` manager, and their JWT subjects differ before creating a session. For both role directions, run checkout-first, hop-first, and simultaneous orderings with distinct naturally frozen end times; ordinary staff SHALL not receive either timing input. Derive the session identity from the acknowledged `start_session`, complete normalized/app-state reads before interception, bind the captured checkout shape to the frontend `FinancialCheckoutV2RpcPayloadEnvelope`, then perform only synchronous `session_updates` assertions before immediate single-send submission. Checkout-first SHALL bill once and reject the stale hop with `session_not_open`; a hop winner SHALL reject the stale ordinary-staff checkout with `invalid_session_timing` and a null mutation result. Reconcile payment sums exactly: a rounded zero-total bill SHALL have zero payment rows, while the positive cash case SHALL have one actor-attributed payment. For a checkout winner, require the exact persisted conflict, Clear, Synced, and Available states; permit only the known pre-send sync guard and optional refreshed-conflict native alert because reload may destroy a delayed alert, and fail any unexpected dialog. Any hopped QA source SHALL then be billed exactly once through `Bill & Done` using the unchanged normalized start/end instants; reconcile exactly one `session_charge` line linked to that source, all cleanup financial rows, and prove cleanup does not advance `app_state`. Pre-send cleanup SHALL positively acknowledge exact-session rejection. No role changes or credential values may be performed, persisted, or attached by the Playwright run.

Explicitly prove that deleting a pause log replaces that session's complete pause-log overlay in the second browser, normalized read failures never show cached financial totals, generic full-state auto-persist is not called, and admin profile plus tab-permission edits commit without `app_state`.

Paginate the Bill Register beyond the bootstrap window and execute each authorized historical action from a loaded page; prove full bill/payment rows are hydrated by ID without dropping unrelated rows. The receipt must resolve split payments, older bills settled during checkout, and both sides of a replacement even when those supporting rows are outside the displayed page. After settlement/replacement/void/refund, the current page must refetch before another action; a late load-more response from before a filter change or same-query refresh must be discarded. For customer analytics, verify session bills use `sessions.started_at`, tab bills use `customer_tabs.opened_at`, replacement-linked session bills retain the original session activity, and counter-only bills use `bills.issued_at`. A missing explicitly linked session must fail closed. A settlement payment returned on both the checkout and source-bill pages must be counted once. Fail the activity query and prove the Customers screen shows retry/read-only state rather than partial analytics.

## Performance

With staging history and app-state size at least production scale, run 50 representative sequential checkouts plus complex and concurrent cases. Require zero SQLSTATE `57014`, deadlocks, duplicate effects, and client timeouts; database p95 below 2 seconds, maximum below 5 seconds, browser completion below 7 seconds; and query plans with no `app_state` access.
